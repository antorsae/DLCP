## FIELD-1: Post-flash app reconnect aborted on both MAINs (flasher) — FIXED

Symptom: flash completes, app reboots, but the flasher reports
`app did not reconnect within 10.0s; last seen devices: <no-product>:unknown`
and raises, skipping the settings restore and the Hypex profile finalize.
Deterministic on both units.

Root cause (two stacked defects in `src/dlcp_fw/flash/dlcp_main_flash.py`):

1. **String-based classification dead-ends.** `_device_mode` classifies a
   device with an empty product string as `unknown`, and `_wait_for_app`
   accepted only `app`-classified devices. macOS can enumerate the
   just-rebooted app with unreadable strings for several seconds (the
   operator's `<no-product>:unknown`), so the wait could NEVER accept the
   device — no timeout value fixes a classifier that rejects the answer.
2. **A 10 s fixed budget** against a V3.4 cold boot that runs the full
   `adc_boot_gate` rail-wait + blocking DSP table apply before the main loop
   services USB.

Fix (implemented):

- `_probe_path_is_app`: identity-probe (cmd `0x06` version exchange) promotes
  string-less devices — the app answers, the bootloader does not. The probe
  is authoritative; enumeration strings become an optimization, not a gate.
- `_wait_for_app` is **event-driven**: it returns the instant the app is
  positively identified, prints progress every ~5 s, and the timeout is only
  a failure ceiling — so the default ceiling was raised to **60 s** at zero
  cost on the success path (`--reconnect-timeout-s` / `--post-info-timeout-s`).
  This is the "smarter than 45 s" design: success latency is governed by the
  device, not the knob.
- **`--finalize-only`** (flasher + release wrappers): completes an aborted
  run — applies and read-back-verifies the IR profile against a running app
  without reflashing. The reconnect-timeout error message now points at it.

Regression tests (green):
`test_field1_wait_for_app_accepts_stringless_device_via_identity_probe`,
`..._rejects_stringless_non_app_and_hints_finalize`,
`..._reconnect_ceilings_are_event_driven_defaults`,
`..._finalize_only_applies_profile_without_flashing`,
`..._info_only_warns_on_rc5_profile`.

## FIELD-2: Remote volume dead, only preset A/B works (RC5 profile)

Symptom: after the flash, Hypex remote volume/mute/power dead; preset A/B
shortcuts still worked.

Root cause chain: the unit was **already on the standard-RC5 profile before
the flash** — the operator's own preflight printed `setup/profile=0x03`
(historic BUG-SETTINGS-01 / boot-clamp residue, see
`docs/IMPL_V171_V32_BUG_LEDGER.md` and the boot clamp at
`dlcp_main_v31.asm:2006-2022`, present in all V3.x: any invalid EEPROM[0x0E]
falls back to `0x03` = standard RC5). The Hypex finalize that would have
fixed it was the exact step FIELD-1 aborted. Under the RC5 map (address
`0x00`) the Hypex remote (address `0x10`) volume arms never match, while the
preset shortcuts still fire — matching the symptom.

Remediation:

- Operator: `dlcp_v34_release_flash.py --path <hid> --finalize-only
  --profile hypex` per unit (no reflash needed), or any future flash (the
  event-driven wait now reaches the finalize).
- `--info-only` now prints a loud WARNING whenever the persisted profile
  differs from the requested/default one, with the finalize-only hint — the
  preflight had the evidence on screen and said nothing.
- Hardening status: the **serial** garbage vector (`B0/1D/0xFF`) was
  sim-tested and the current firmware already rejects it — pinned green by
  `test_field2_serial_cmd1d_garbage_must_not_corrupt_profile` (this corrects
  the 2026-06-10 audit's assumption that the serial path was unclamped). The
  **HID setup-byte write** (`dlcp_main_v34.asm` `flow_hid_command_dispatch_114a`,
  host report byte -> RAM `0x0B8` unclamped, persisted to EEPROM[0x0E])
  remains an open clamp item.

## FIELD-3: Preset page row 0 blank after STBY/WAKE while parked on it

Symptom: park on the Preset page, standby, wake — row 0 is sixteen blanks
while row 1 renders. Field confirmation of the exploratory `s0026`/`s0099`
residual.

Sim repro + root cause (tick-bisected): after the reconnect WAITING exits,
the resume path **runs the Preset entry repaint first** (row 0 painted,
`FNAME_ROW0_NOT_READY` cleared, filename re-queried) **and then blanks the
whole LCD** — leaving row 0 empty while the lifecycle state says "painted",
so the row-1 renderer proceeds. An order inversion in the post-wake resume
(`post_connect_init` region), not a filename-machinery bug; the round-1
BUG-3 invalidate works as designed but is undone by the late blank.

Fix (implemented 2026-06-11, three layers in `dlcp_control_v173.asm`):

1. `app_entry_defensive_stub` (the only runtime full-LCD clear) now calls
   `v173_preset_lcd_invalidate` -- any defensive clear marks row 0 not-ready.
2. The row-0 paint was factored into `v173_preset_row0_paint` and the
   per-pass filename service SELF-HEALS: not-ready + awake/CONNECTED ->
   repaint row 0 (suppressed during standby/WAITING so the Zzz/banner
   overlays keep LCD ownership).
3. Belt: `v173_row0_reassert_div` (bank2 0x25E) re-asserts row 0 every 32
   service passes while parked awake on the Preset page -- mechanism-
   agnostic recovery for any blanking path that outruns the flag
   bookkeeping (rewriting identical characters is invisible on HD44780).

Deep-dive finding (Addendum below): the post-wake bounce can corrupt one
LCD byte sequence; the entry repaint had ALREADY run and cleared the
not-ready latch when a later blank landed, which is why flag bookkeeping
alone could never be trusted and the periodic re-assert is the load-bearing
layer.

Regression (green): `test_field3_preset_page_row0_survives_standby_wake_while_parked`.

## FIELD-4 (SAFETY): Loud bass on preset B switch — two defects

Symptom: switching A->B while listening produced dangerously loud bass
(wrong crossover content on a woofer channel); muted manually; cycling A->B
again sounded correct. Transient, first-switch.

### FIELD-4A — NACKed coefficient writes are silently skipped (primary)

Sim repro: inject TAS3108 I2C data NACKs at the moment of the switch (the
model for a real bus glitch at switch time). Result: the job walks
"successfully", COMMITs, **restores full volume with the DSP still holding
the preset-A image while the firmware reports preset B — and
`dsp_fault=0x00`, nothing surfaced.** Root cause:
`preset_job_apply_i2c_entry` treats only bounded START/STOP **timeouts** as
retryable; per-entry **ACK failures are never checked** — the verified-write
contract (`volume_dsp_write`'s ACKSTAT check, retries, BF/08) exists only
for volume writes, never for the preset table apply. A half-or-un-applied
crossover at full volume is exactly the field incident.

Fix (implemented 2026-06-11): `preset_job_apply_i2c_entry` clears the
shared `i2c_byte_tx` ACKSTAT latch (`dsp_fault_flags.2`) before each entry
and treats a latched NACK exactly like a bounded timeout -- C=1, the caller
retries THIS entry with `i2c_timeout_recover_advertise` running in between
(visible diag counters, bus recovery, audio stays force-muted).  A
persistently dead bus parks the job muted instead of committing a wrong
image.

Regression (green):
`test_field4a_preset_apply_with_tas_nacks_must_not_unmute_wrong_image`.

### FIELD-4B — COMMIT unmutes before the post-switch DSP stage completes

Sim repro (clean path, no faults): at COMMIT the volume is restored while
`event_flags.6` route/mixer work is still queued; the channel mixer/trim
registers (`0x32-0x36` and parts of `0x37-0x90`) are written **after** the
unmute — audio live through a half-reconfigured DSP for at least one
dispatch pass, unbounded if that stage stalls. Introduced by the V3.2 async
preset job split (stock applied everything before restoring volume).

Fix (implemented 2026-06-11, simpler than the original plan): the deep
cause was that the preset capture tables BAKE the volume-family registers
(TAS `0x30-0x36`, master + per-channel volumes) and the muted job walk
applied those capture-time values; the volume engine then re-derived and
overwrote them right after the unmute -- so the baked values were only ever
a transient hazard window.  `preset_table_apply_entry_core` now SKIPS
volume-family rows (`0x30 <= reg <= 0x36`): the user's channel volumes stay
correct end-to-end, the post-unmute engine re-walk rewrites identical
values, and the behavior after settle is unchanged by construction.  This
also applies to the legacy blocking boot apply, where the master volume is
already zeroed before the walk (no-pop ordering), so boot stays silent
until the volume engine restores user volume.

Cost note: FIELD-4A+4B together spent ~20 bytes of MAIN reserve; the
listing-headroom floor was consciously lowered 128 -> 96 bytes in
`test_v34_v173_refactoring_contracts.py` (margin now 108 bytes).  Recover
in the next size campaign.

Regression (green):
`test_field4b_no_dsp_coefficient_writes_after_preset_unmute`.

Interim operator guidance until 4A/4B land: **mute before preset switches,
unmute a couple of seconds after** — the walk itself is force-muted; manual
mute brackets both defect windows.

## Why the test system missed these — honest gap analysis and closures

**The exploratory system found three of the four classes; the failure was
triage, plus two structural blind spots.**

1. **FIELD-4A was flagged and de-prioritized.** The 2026-06-10 exploratory
   report contained both halves of the evidence: `s0002`/`s0011` ("under TAS
   NACK/retry pressure firmware can report muted while the last TAS30 is
   nonzero") and `s0029` (same-preset idle DSP digest divergence under
   churn). The triage — including this assistant's own day-to-day assessment
   — classed it "fault-injection robustness, ~zero daily impact". That was
   wrong: NACK injection is precisely the model for real I2C glitches at the
   instant of a preset switch. *Closure:* the deterministic invariant test
   now pins it (xfail -> green with the fix); lesson recorded: **a finding
   whose failure mode is "audio live on wrong coefficients" is a safety
   class and must never be triaged on stimulus exoticism.**
2. **FIELD-4B was invisible to both test layers by construction.** Standard
   tests assert *settled* state (settle-then-check), and the exploratory
   observer samples every ~1-3 s — the unsafe window is ~tens of ms. No
   oracle ever related *unmute time* to *pipeline completion*. *Closure:*
   the new invariant test samples at 250k-tick granularity across the switch
   and asserts the image is final from the first unmuted sample; planned
   harness follow-up: a high-rate window detector around preset stimuli (or
   a rust-side "DSP writes while unmuted post-job" counter) so exploratory
   runs can see sub-observation windows.
3. **FIELD-3 was found (s0026) and queued behind minimization.** The
   deterministic suites missed it because the standby/wake LCD tests always
   navigated AWAY from Preset before STBY (`..._preset_b_survives_next_menu_
   standby_wake` goes Preset->Input->STBY); nobody parked ON the page.
   *Closure:* the new test parks on Preset; follow-up: parametrize
   standby/wake row-atomicity across ALL display states.
4. **FIELD-1/2 lived in the only layer with zero coverage: live hardware.**
   Every flasher test stubbed enumeration with instant, fully-stringed
   devices; no test modeled slow or string-less re-enumeration, and the
   ledger's hardware gates had not been run against rev 0x81 before
   deployment. *Closure:* the string-less/slow-enumeration paths are now
   unit-tested against the probe-based wait; `--info-only` warns on profile
   mismatch instead of silently displaying it; `--finalize-only` makes an
   aborted ceremony recoverable. Process note: the runbooks' "hardware smoke
   is the release gate" requirement is real — this incident is what it
   exists to catch.

## Addendum (2026-06-11): findings from the FIELD-3 forensics

1. **Post-wake standby-path bounce.**  Tick-level traces show the wake
   sequence can re-enter the standby path after the Preset entry repaint
   already ran (`'Preset         A'` visible, then blanked 0.3M ticks later
   with the PC inside `app_entry_defensive_stub`'s delay), and a duplicated
   wake press can be consumed twice (one LEFT press from the buggy state
   landed two menu states away).  The FIELD-3 layers make the LCD outcome
   robust regardless; the button/event double-consume itself is a candidate
   for a future dedicated fix.
2. **Stock-latent ISR/foreground scratch collision — FIXED 2026-06-11
   (V1.73 rev 0x44).**  Final mechanism, after two corrected hypotheses:
   the stock RC5 decoder runs BLOCKING inside the ISR (~7-10 ms from the
   first edge) and clobbers access-bank scratch shared with the foreground
   LCD/delay helpers (`0x005`, `0x008`, `0x00C..0x00E`, the `0x010..0x013`
   sample buffer, `0x014/0x015`).  The V1.71 health-suffix patch knew this
   and GIE-masked its own LCD writes -- which protected the LCD at the
   cost of EATING any IR frame that landed inside the mask (RBIF latches,
   but a late-entered blocking decoder cannot sample the frame).  All
   stock LCD sections stayed unmasked, so an IR frame mid-draw corrupted
   the interrupted sequence instead -- the historic LCD-glitch class and a
   credible mechanism for the field FIELD-3 row-0 blank (the wake press
   arrived by IR remote with repeats).  Fix: the ISR saves the full
   shared-scratch set before `rcall ir_rc5_decode` and restores it after
   the result stores (`v173_isr_decode_save`, bank2 0x260..0x26A), and the
   now-purposeless GIE mask in the health patch is retired.  IR decodes
   correctly during foreground LCD/delay activity AND the interrupted
   foreground state survives; the decode logic itself is untouched
   (BUG-IR-01 hardware-validated path).  Tests:
   `tests/sim/test_v17x_isr_scratch_collision.py` (baseline decode pin,
   decode-survives-foreground-delay, count-survives behavioral check
   [skips when the phase-dependent catch cannot be established], and the
   structural save/restore + no-GIE-mask pin).
   Original (superseded) text follows for the record:
   Corrected mechanism after the 2026-06-11 sim reproduction
   (`tests/sim/test_v17x_isr_scratch_collision.py`, 1 baseline pin green +
   2 strict-xfail contracts): the in-ISR RC5 decoder uses `Common_RAM+12/13`
   as its per-edge TIMING scratch and (after the timing phase) as its
   address/command accumulators -- on an idle foreground the decode is
   untouched and correct, so the load-bearing collision is the shared
   delay/timing use, not background accumulation as first hypothesized --
   while every foreground `control_core_service_01D8` delay
   decrements the very same cells in place.  When an IR edge interrupts a
   foreground delay loop, both directions corrupt, deterministically
   reproduced: (a) the in-flight foreground count corrupts the decoder's
   edge timing and the frame FAILS TO DECODE -- a silently dropped remote
   press, matching the field symptom "remote is flaky while the display is
   busy"; (b) the decoder residue rewrites the interrupted delay's
   remaining count (observed `0x0019 -> 0x0205`, ~20x inflation) -- LCD
   timing distortion on real hardware.  Present in stock V1.6b; carried
   into V1.7x by the byte-faithful rewrite.  Fix contract pinned by the
   xfails: preserve the foreground's `0x00C/0x00D` across the ISR decode
   (save/restore in the ISR prologue/epilogue, or dedicated decoder
   cells), without touching the hardware-validated decode logic.
3. **Test-arming race fixed.**  The full-sync stepper fires on EXACT
   equality with `0x4E20`; `test_v173_v34_chain_mute_survives_periodic_
   full_sync_refresh` armed the counter at exactly `0x4E20`, racing the
   per-pass increment (a one-increment miss waits a full 16-bit wrap).  The
   test now arms one below (`0x4E1F`), firing within two passes under
   either ordering.

## Addendum 2 (2026-06-11): session-49 mute escape — lost-frame convergence

Exploratory run `20260611_100415_goal_subagents_isr_scratch_20m` session 49:
a held SELECT (the stock mute toggle, which auto-repeats into an
unmute-then-mute pair) left **PB1 unmuted at full volume while CONTROL
displayed Mute and PB2 stayed muted** — a true awake mute-ownership escape.

Forensics (fully deterministic via instrumented replay):

1. CONTROL emitted `B0/03/03` then `B0/03/02`, 41.8M ticks apart.  Both
   frames reached PB1's UART FIFO **byte-perfect** (363/363 TX bytes
   FIFO-accepted, streams identical) and PB2 (downstream through PB1's
   forwarding) applied both.
2. PB1's `cmd03_mute_on_handler` **never executed** for the second frame
   (PC-watch: zero hits across the delivery window); the parser consumed
   the bytes misaligned (caught mid-frame at idle, `fpos=1` with
   `rd==wr`), under the session's sustained TAS-NACK foreground pressure.
   The exact instruction-level loss inside the ring/parser is still open
   (tracked below); the byte-level layer is fully exonerated.
3. Nothing ever healed the divergence: the CONTROL cmd-03 echo path only
   syncs CONTROL *toward* MAINs, and the full-sync mute step's counter is
   reset by every volume frame — session 49's host-volume cadence starved
   it indefinitely.  Mute was the only chain state without a working
   convergence loop.

Fix (V1.73 rev 0x47): **periodic idempotent mute re-assert** — riding the
health-poll cadence, every 2nd successful poll enqueue *while CONTROL is
muted and connected*, re-broadcast `B0/03/02`
(`v173_mute_reassert_div`, bank2 0x26B).  A consistent MAIN no-ops the
redundant frame; a diverged MAIN re-converges within ~2 poll cycles.  The
muted-only gate keeps the idle/unmuted wire byte-identical to rev 0x44
(test phase assumptions hold; the dangerous direction — live audio against
a muted UI — is the one that self-heals).  Replaying session 49 against the
fixed canonical shows both PBs muted and consistent at the original escape
observation point.

Review hardening (codex on `b1f35d6`, fixed in the follow-up): the first
implementation routed the re-assert through `mute_frame_send` ->
`serial_tx_routed_frame`, whose success path clears the full-sync
countdown — so while muted, the mute convergence loop starved the
volume/input/preset full-sync convergence indefinitely.  The re-assert now
enqueues the frame with the raw tx-ring primitives (no full-sync side
effect), STATUS.C is forced back to the poll's result on every re-assert
path, and `test_v173_mute_reassert_does_not_starve_full_sync` pins an
armed full-sync firing while muted with re-asserts flowing.  The
rotation-tolerant LCD helper was also tightened to the scroller's real
bounce behavior (contiguous substrings only, no circular wrap).

Tests: `test_v34_serial_remute_applies_after_recent_unmute` (a chain mute
must always apply regardless of how recently an unmute ran) and
`test_v173_chain_mute_state_converges_after_lost_mute_frame` (a diverged
MAIN re-converges within a bound far tighter than the starvable
full-sync), both in `tests/sim/test_v34_mute_refresh_bug.py`.  Filename
LCD suites made rotation-tolerant where they pinned exact scroll phases.

Residuals tracked: (a) the instruction-level parser/ring loss mechanism
under I2C-retry pressure (forensic breadcrumbs above; affects any single
frame, but every other chain state already had convergence); (b) the
reverse direction — a MAIN stuck muted while CONTROL is unmuted — is not
covered by the muted-only re-assert (cosmetically a silent speaker, not a
safety issue; the cmd-03 echo adopt path partially covers it).
