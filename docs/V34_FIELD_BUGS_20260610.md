## FIELD-1: Post-flash app reconnect aborted on both MAINs (flasher) — FIXED

Symptom: flash completes, app reboots, but the flasher reports
`app did not reconnect within 10.0s; last seen devices: <no-product>:unknown`
and raises, skipping the settings restore and the Hypex profile finalize.
Deterministic on both units.

Root cause (two stacked defects in `src/dlcp_fw/flash/dlcp_main_flash.py`):

1. **String-based classification dead-ends.** `_device_mode` classifies a
   device with an empty product string as `unknown`, and `_wait_for_app`
   accepted only `app`-classified devices. macOS can enumerate the
   just-rebooted app with unreadable strings for several seconds (the
   operator's `<no-product>:unknown`), so the wait could NEVER accept the
   device — no timeout value fixes a classifier that rejects the answer.
2. **A 10 s fixed budget** against a V3.4 cold boot that runs the full
   `run_wake_rail_gate_and_dsp_cold_init` rail-wait + blocking DSP table apply before the main loop
   services USB.

Fix (implemented):

- `_probe_path_is_app`: identity-probe (cmd `0x06` version exchange) promotes
  string-less devices — the app answers, the bootloader does not. The probe
  is authoritative; enumeration strings become an optimization, not a gate.
- `_wait_for_app` is **event-driven**: it returns the instant the app is
  positively identified, prints progress every ~5 s, and the timeout is only
  a failure ceiling — so the default ceiling was raised to **60 s** at zero
  cost on the success path (`--reconnect-timeout-s` / `--post-info-timeout-s`).
  This is the "smarter than 45 s" design: success latency is governed by the
  device, not the knob.
- **`--finalize-only`** (flasher + release wrappers): completes an aborted
  run — applies and read-back-verifies the IR profile against a running app
  without reflashing. The reconnect-timeout error message now points at it.

Regression tests (green):
`test_field1_wait_for_app_accepts_stringless_device_via_identity_probe`,
`..._rejects_stringless_non_app_and_hints_finalize`,
`..._reconnect_ceilings_are_event_driven_defaults`,
`..._finalize_only_applies_profile_without_flashing`,
`..._info_only_warns_on_rc5_profile`.

## FIELD-2: Remote volume dead, only preset A/B works (RC5 profile)

Symptom: after the flash, Hypex remote volume/mute/power dead; preset A/B
shortcuts still worked.

Root cause chain: the unit was **already on the standard-RC5 profile before
the flash** — the operator's own preflight printed `setup/profile=0x03`
(historic BUG-SETTINGS-01 / boot-clamp residue, see
`docs/IMPL_V171_V32_BUG_LEDGER.md` and the boot clamp at
`dlcp_main_v31.asm:2006-2022`, present in all V3.x: any invalid EEPROM[0x0E]
falls back to `0x03` = standard RC5). The Hypex finalize that would have
fixed it was the exact step FIELD-1 aborted. Under the RC5 map (address
`0x00`) the Hypex remote (address `0x10`) volume arms never match, while the
preset shortcuts still fire — matching the symptom.

Remediation:

- Operator: `dlcp_v34_release_flash.py --path <hid> --finalize-only
  --profile hypex` per unit (no reflash needed), or any future flash (the
  event-driven wait now reaches the finalize).
- `--info-only` now prints a loud WARNING whenever the persisted profile
  differs from the requested/default one, with the finalize-only hint — the
  preflight had the evidence on screen and said nothing.
- Hardening status: the **serial** garbage vector (`B0/1D/0xFF`) was
  sim-tested and the current firmware already rejects it — pinned green by
  `test_field2_serial_cmd1d_garbage_must_not_corrupt_profile` (this corrects
  the 2026-06-10 audit's assumption that the serial path was unclamped). The
  **HID setup-byte write** (`dlcp_main_v34.asm` `hid_command_dispatch__opcode04_stage_fault_action`,
  host report byte -> RAM `0x0B8` unclamped, persisted to EEPROM[0x0E])
  remains an open clamp item.

## FIELD-3: Preset page row 0 blank after STBY/WAKE while parked on it

Symptom: park on the Preset page, standby, wake — row 0 is sixteen blanks
while row 1 renders. Field confirmation of the exploratory `s0026`/`s0099`
residual.

Sim repro + root cause (tick-bisected): after the reconnect WAITING exits,
the resume path **runs the Preset entry repaint first** (row 0 painted,
`FNAME_ROW0_NOT_READY` cleared, filename re-queried) **and then blanks the
whole LCD** — leaving row 0 empty while the lifecycle state says "painted",
so the row-1 renderer proceeds. An order inversion in the post-wake resume
(`post_connect_init` region), not a filename-machinery bug; the round-1
BUG-3 invalidate works as designed but is undone by the late blank.

Fix (implemented 2026-06-11, three layers in `dlcp_control_v173.asm`):

1. `app_entry_defensive_stub` (the only runtime full-LCD clear) now calls
   `v173_preset_lcd_invalidate` -- any defensive clear marks row 0 not-ready.
2. The row-0 paint was factored into `v173_preset_row0_paint` and the
   per-pass filename service SELF-HEALS: not-ready + awake/CONNECTED ->
   repaint row 0 (suppressed during standby/WAITING so the Zzz/banner
   overlays keep LCD ownership).
3. Belt: `v173_row0_reassert_div` (bank2 0x25E) re-asserts row 0 every 32
   service passes while parked awake on the Preset page -- mechanism-
   agnostic recovery for any blanking path that outruns the flag
   bookkeeping (rewriting identical characters is invisible on HD44780).

Deep-dive finding (Addendum below): the post-wake bounce can corrupt one
LCD byte sequence; the entry repaint had ALREADY run and cleared the
not-ready latch when a later blank landed, which is why flag bookkeeping
alone could never be trusted and the periodic re-assert is the load-bearing
layer.

Regression (green): `test_field3_preset_page_row0_survives_standby_wake_while_parked`.

## FIELD-4 (SAFETY): Loud bass on preset B switch — two defects

Symptom: switching A->B while listening produced dangerously loud bass
(wrong crossover content on a woofer channel); muted manually; cycling A->B
again sounded correct. Transient, first-switch.

### FIELD-4A — NACKed coefficient writes are silently skipped (primary)

Sim repro: inject TAS3108 I2C data NACKs at the moment of the switch (the
model for a real bus glitch at switch time). Result: the job walks
"successfully", COMMITs, **restores full volume with the DSP still holding
the preset-A image while the firmware reports preset B — and
`dsp_fault=0x00`, nothing surfaced.** Root cause:
`preset_job_apply_i2c_entry` treats only bounded START/STOP **timeouts** as
retryable; per-entry **ACK failures are never checked** — the verified-write
contract (`volume_dsp_write`'s ACKSTAT check, retries, BF/08) exists only
for volume writes, never for the preset table apply. A half-or-un-applied
crossover at full volume is exactly the field incident.

Fix (implemented 2026-06-11, strengthened 2026-06-14): `preset_job_apply_i2c_entry`
treats a latched ACKSTAT (`dsp_fault_flags.2`) exactly like a bounded timeout
-- C=1, the caller retries THIS entry with `i2c_timeout_recover_advertise`
running in between (visible diag counters, bus recovery, audio stays
force-muted).  FIELD-10 follow-up made the entry fail fast on a pre-existing
ACKSTAT instead of clearing it and continuing, so an active7 zero-mute NACK
cannot be erased just before coefficient rows start.  A persistently dead bus
parks the job muted instead of committing a wrong image.

Regression (green):
`test_field4a_preset_apply_with_tas_nacks_must_not_unmute_wrong_image`.

### FIELD-4B — COMMIT unmutes before the post-switch DSP stage completes

Sim repro (clean path, no faults): at COMMIT the volume is restored while
`event_flags.6` route/mixer work is still queued; the channel mixer/trim
registers (`0x32-0x36` and parts of `0x37-0x90`) are written **after** the
unmute — audio live through a half-reconfigured DSP for at least one
dispatch pass, unbounded if that stage stalls. Introduced by the V3.2 async
preset job split (stock applied everything before restoring volume).

Fix (implemented 2026-06-11, simpler than the original plan): the deep
cause was that the preset capture tables BAKE the volume-family registers
(TAS `0x30-0x36`, master + per-channel volumes) and the muted job walk
applied those capture-time values; the volume engine then re-derived and
overwrote them right after the unmute -- so the baked values were only ever
a transient hazard window.  `preset_table_apply_entry_core` now SKIPS
volume-family rows (`0x30 <= reg <= 0x36`): the user's channel volumes stay
correct end-to-end, the post-unmute engine re-walk rewrites identical
values, and the behavior after settle is unchanged by construction.  This
also applies to the legacy blocking boot apply, where the master volume is
already zeroed before the walk (no-pop ordering), so boot stays silent
until the volume engine restores user volume.

Cost note: FIELD-4A+4B together spent ~20 bytes of MAIN reserve; the
listing-headroom floor was consciously lowered 128 -> 96 bytes in
`test_v34_v173_refactoring_contracts.py` (margin now 108 bytes).  Recover
in the next size campaign.

Regression (green):
`test_field4b_no_dsp_coefficient_writes_after_preset_unmute`.

Interim operator guidance until 4A/4B land: **mute before preset switches,
unmute a couple of seconds after** — the walk itself is force-muted; manual
mute brackets both defect windows.

## FIELD-5 (SAFETY, FIXED in MAIN V3.4 rev 0x9A): Preset A/B switching can commit a mixed DSP image

Symptom (2026-06-13 live rig, MAIN `V3.4 rev 0x96`, CONTROL `V1.73 rev 0x47`):
while listening normally on `LX521.4 22MG10F-v5`/`v7`, repeated IR A/B
switching eventually produced a dramatic filter change; bass became extreme
enough to risk speaker damage.  Diagnostics still printed `HEALTHY`, both
MAINs reported the requested preset and route, and the LCD showed a normal
Volume page.

Deterministic sim repro: drive B->A at a specific phase on the two-MAIN chain.
PB2 reaches `preset_job_state=IDLE`, `active_flags.bit2=0` (preset A), clears
the effective mute bit, restores a nonzero TAS `0x30` master-volume payload,
and shows `Volume:-17.0dB A`, but its TAS coefficient image does not match the
clean preset-A image.  The first observed differing register is TAS `0x59`:
expected `0x00`, observed `0x7F`.

Evidence narrowing:

1. The baked release hex is correct.  Logical table rows `0x5960` and `0x5978`
   contain the expected headers `0x58/0x14` and `0x59/0x14` in both A and B
   windows.
2. The bad PB2 write log contains the TAS `0x58` burst but omits the TAS
   `0x59` burst.  Because the `0x58` burst overlaps register `0x59`, it leaves
   `0x59=0x7F`; the missing `0x59` burst would have overwritten that byte with
   the correct preset-A value.  The stale/wrong header value observed in the
   failing APPLY window is also `0x7F`, consistent with `flash_read_to_scratch_buffer`
   reusing the same access-bank scratch window (`0x17..`) for row headers and
   row payloads without a transaction/validity check.
3. The failure reproduces without TAS NACKs, bus faults, or DSP fault flags.
   FIELD-4A therefore did not cover it.
4. The SRC4382 RXCKR hole is not the root cause.  It is a timing trigger:
   the same missing-`0x59` PB2 image reproduces with no SRC register
   perturbation when the IR B->A command lands in the bad phase.

Root-cause statement: the V3.4 async preset APPLY path could read or act
on a wrong preset-table header for PB2, skip/direct the TAS `0x59` entry, then
`COMMIT` because the state machine only proves that its logical index advanced
to the end.  It does not prove that the row selected by `preset_job_index` was
the row just read, or that every required DSP coefficient row was emitted
before unmute.  The direct MAIN ISR path is not the leading explanation:
Timer0/Timer3/UART ISR handling saves/restores W/STATUS/BSR via FAST plus
FSR2 manually, and does not touch TBLPTR/TABLAT/header scratch.  The
low-level phase trigger remains secondary; the audio-safety root cause was the
missing APPLY-row validity proof.

Conclusive low-level proof still desired: trace PB2 row `0x5978` and show
`TABLAT=0x59` during the flash read while RAM `0x018`/`stock_02F` remains or
becomes `0x7F`, followed by a TAS write to `0x7F` and no TAS `0x59` write.
The current sim repro already proves the audio-safety failure without that
last instruction-level capture.

Fix implemented in MAIN `V3.4 rev 0x9A`:

1. Make APPLY use an immutable job-owned table source.  At HOLDING->APPLY,
   derive the physical preset table base from the requested target and store
   it in preset-job state, rather than relying on live `active_flags.bit2`
   remap during each flash read.
2. Validate every APPLY header from `preset_job_index` before writing TAS or
   advancing the index.  The expected sequence is derivable without a large
   table: index `0x60` is final row `0xD4/0x04`; group rows where
   `index & 0x0F == 0` are `0xC8 + (index >> 4)` with length `0x04`; other
   coefficient rows are the `0x37..0x90` 20-byte rows, skipping the existing
   volume-family `0x30..0x36` policy.  On mismatch, retry/recover and stay
   force-muted; do not advance to COMMIT.
3. Keep audio muted until the final validated entry succeeds.  `COMMIT` must
   be a consequence of "selected preset image emitted", not merely "loop
   counter reached the end".
4. During broad-gate verification, tighten Auto Detect route changes so route
   churn does not dirty master volume while unmuted; muted route refresh still
   enters the existing zero-write path.  This preserves the FIELD-4 mute
   contract and closes the detect-cycle louder-volume regression exposed by
   `tests/sim/test_v34_detect_cycle_volume_excursion.py`.

A solution that only retries after one observed bad register, or special-cases
TAS `0x59`, is explicitly rejected.  Structural hazards found during review
(`chain_copy` TOS access with interrupts enabled; ISR spill-slot aliases) must
be fixed/audited separately, but they are not enough by themselves to explain
this APPLY signature.

Regression tests are now green with the former strict XFAIL markers removed:
`tests/sim/test_v34_preset_src_hole_field_bug.py::test_ir_b_to_a_under_locked_rxckr_hole_never_unmutes_wrong_pb2_coefficients`
and
`tests/sim/test_v34_preset_src_hole_field_bug.py::test_ir_b_to_a_phase_hit_without_src_hole_never_omits_pb2_tas59_write`.

Final simulator evidence for rev `0x9A`: focused FIELD-5 `8 passed`; safety
group `81 passed, 1 xfailed` (known `chain_copy` proof); broader filtered gate
`599 passed, 1 xfailed`; full `tests/sim -n 16` gate `1590 passed, 2 skipped,
1 xfailed`.

## FIELD-6-DSP (SAFETY, FIXED in V3.4 rev 0xA0): Wake route-sync can overwrite a clean preset image after blocking apply

Symptom/repro (2026-06-13 sim, pre-fix MAIN `V3.4 rev 0x9A` lineage, CONTROL
`V1.73`): the exact session-5-style sequence in
`tests/sim/test_v34_v173_field_repros_20260613.py::test_session5_power_toggle_never_restores_live_audio_on_wrong_a_coefficients`
was strict-XFAIL before the fix.  The sequence is:

1. learn a clean preset-A TAS `0x37..0x90` image after a full B->A apply;
2. boot a two-MAIN chain with session-5 filename slots and `mclr` reset;
3. press front-panel `STBY`, wait `7_999_364` ticks;
4. press front-panel `STBY` again;
5. inject IR power, wait `1_581_503` ticks;
6. inject IR power again;
7. assert that no MAIN reports live/committed preset A with a different TAS
   coefficient image.

Observed failure: after the second IR power, both MAINs report a normal-looking
awake state (`Volume:-17.0dB A`, connected, gates up, preset A, job idle,
no DSP fault flags, SRC locked).  Their settled coefficient digest is
`40436d84c08b` instead of the clean preset-A digest `527246c85ab5`; the first
diff is TAS `0x37`, expected `0x0f`, observed `0x00`.

Important nuance in the original XFAIL oracle: it treated a nonzero *last direct*
TAS `0x30` write as live audio.  The actual TAS `0x30..0x33` registers at the
exact post-power observation are zero, because the same later route-sync burst
also overlaps and clears them.  This does not make the bug benign: a subsequent
normal volume write restores TAS `0x30` while the bad coefficient image remains
`40436d84c08b`, making the wrong image audibly live.

Root cause: this is not the fixed FIELD-5 async APPLY missing-row bug.  It is a
DSP ownership/order bug in the wake/reconnect lifecycle:

1. `run_wake_rail_gate_and_dsp_cold_init` mutes, runs the full blocking preset-table apply via
   `preset_replay_selected_table_blocking`, and therefore creates the clean preset image.
2. The same wake path then sets `event_flags.bit4` and immediately calls
   `cmd_dispatch_gated`.
3. `cmd_dispatch_gated` services bit4 by calling `i2c_apply_channel_route_sync_burst`, the
   composite route/channel sync burst.
4. `i2c_apply_channel_route_sync_burst` emits TAS bursts starting at `0x21`, `0x22`,
   `0x23`, `0x25`, `0x27`, and `0x28`, followed by a direct `0x30` volume
   restore.  The TAS3108 auto-increments inside a burst; the `0x28` burst is
   sixteen bytes long and reaches register `0x37`, overwriting preset A's
   expected `0x0f` with `0x00`.

Isolated write-log proof for the second IR-power transition, with DSP write logs
reset immediately before the second power command:

```text
before second IR power:
  unit0 digest 527246c85ab5, TAS 0x37 = 0x0f, TAS 0x30..0x33 = 00000000

after second IR power:
  0x21-0x30 00000000008000000000000000000000
  0x22-0x31 00000000008000000000000000000000
  0x23-0x32 00000000008000000000000000000000
  0x25-0x34 00000000000000000080000000000000
  0x27-0x36 00000000000000000000000000000000
  0x28-0x37 00800000000000000000000000000000
  0x30-0x33 00120bdb
  coefficient digest 40436d84c08b, first diff (0x37, 0x0f -> 0x00)
```

Fix contract: preset coefficient ownership must be final before audio is
declared live.  Any wake/reconnect route/channel sync that can write into
`0x37..0x90` must either run before the final preset image is applied, or must
be followed by a bounded, validated preset-coefficient reassert before unmute or
volume restore.  The final preset writer in this lifecycle must use the
FIELD-5 physical-source/header-validation/NACK-aware contract or an equivalent
proof; a plain legacy blocking `preset_replay_selected_table_blocking` re-walk is not an
acceptable final safety writer.  A solution that special-cases TAS `0x37`,
relies on sleeps, or only changes the Python oracle is rejected.  The XFAIL
oracle itself must also be tightened to use actual TAS `0x30..0x33` register
contents for live-audio state and to prove that a later volume write cannot
make a stale/bad coefficient image live.  The existing Diagnostics-page STBY
strict XFAIL in `tests/sim/test_v34_v173_field_repros_20260613.py` is a separate
CONTROL/UI issue and is out of scope for FIELD-6-DSP.

Resolution (V3.4 rev `0xA0`):

- `cmd_dispatch_gated` now factors `event_flags.bit1` input-route work into
  `cmd_dispatch_input_route_if_dirty`; the bit4 route/channel-sync tail is
  owned by `cmd_dispatch_route_sync_if_dirty`.
- The `active_flags.bit7` lifecycle/reconnect owner drains bit4 route/channel
  sync while muted, clears deferred bit6 before final reassert, and uses the
  FIELD-5 validated physical-source/header/NACK-aware row writer through
  `preset_replay_selected_table_blocking`.  FIELD-10 superseded the original bit1 ordering:
  input-route side effects are now isolated until after the post-wake
  `i2c_secondary_apply_wake_init_table` barrier succeeds.
- Wake no longer has an independent final-writer sequence.  It writes TAS
  volume zero, marks bit4 dirty, arms `active_flags.bit7`, runs the validated
  lifecycle owner, then performs the FIELD-10 barrier and late bit1 phase
  before any nonzero volume restore.  The full dispatcher call in wake is
  guarded by the lifecycle bypass before any bit3/bit6 service; it is not the
  rejected pre-fix "route drain by full dispatch" shortcut.
- FIELD-6 live-audio oracles now use actual TAS `0x30..0x33` registers and
  golden selected-preset images.  Wake/reconnect failure tests cover TAS
  address NACK, TAS data NACK, row-header mismatch, and MSSP STOP timeout, and
  verify recovery before any live wrong-image state.
- The lifecycle owner now guards its filename critical section with the current
  GIE state so wake cannot inherit an unconditional `bsf INTCON,7`.
- The V3.2 `i2c_apply_channel_route_sync_burst` table guard is parameterized for V3.2 and
  V3.4 so route-sync table shape stays pinned across both source lines.

## FIELD-7-DSP (SAFETY, FIXED IN SIM): Preset phase sweep can leave live audio on a non-golden coefficient image

Source evidence: 30-minute exploratory run
`artifacts/sim/current/exploratory/20260613_rerun_30m_subagent_judges`,
card `cards_all/20260613_211929_573cba82a35d9fef__s0001.md`, session 1
(`preset-phase-sweep`, no synthetic fault load).  After
`IR:preset_b`, 160M ticks, `IR:preset_a`, 160M ticks, then a 12.174408M tick
phase delay, PB1 is awake, unmuted, fault-free, idle, and reports preset A,
but its TAS coefficient digest is `054b166d80e6` instead of golden preset-A
`527246c85ab5`.  The first byte difference is TAS subaddress `0x4E`:
expected `0x00`, observed `0x01`.  PB2 remains on the golden A image.

Why this is a new bug: FIELD-5 fixed missing/incorrect APPLY rows during a
blocking preset transaction; FIELD-6 fixed wake/reconnect route-sync as an

## FIELD-9 (TRANSPORT/RAM SAFETY, CONTAINED in V3.4 rev 0xA6): current-loop bytes in filename/config RAM

Symptom (2026-06-14 live rig, MAIN `V3.4 rev 0xA5`): after release flashing
and then running diagnostics watch, the flasher printed preset B active
filename as `4c583532312e342032324d47313046bf7637`
(`LX521.4 22MG10F` + `0xBF` + `v7`) instead of `...2d7637` (`-v7`).
`scripts/dlcp_diag.py` then reported a Config field containing repeated
current-loop frame cadence:
`00bf2c00b12300bf2c00b12300bf2c00b12300b12300bf2c00b12300bf2c`, with
impossible mixed channel mapping and `i2c_transport_faults=6`.  CONTROL LCD
also showed shared-path uncertainty (`!1 2`) while repeated JSON watch was
running.

Proven mechanism: MAIN's UART RX ISR stored `RCREG` through
`FSR2 = 0x0200 + rx_ring_wr` before proving `rx_ring_wr < 0xC0`.  If
`rx_ring_wr` is corrupt/out-of-range, a normal current-loop byte is written
outside the 0x0200..0x02BF RX ring.  The live `0xBF` byte at filename offset
15 maps exactly to `rx_ring_wr = 0xCF` (`0x0200 + 0xCF = 0x02CF`, the `-` in
`LX521.4 22MG10F-v7`).  A focused regression seeds that condition and proves
the pre-store clamp keeps the byte in ring[0] and preserves the filename.

Fix/containment in MAIN `V3.4 rev 0xA6`: `uart_rx_irq_enqueue` now clamps an
invalid `rx_ring_wr >= 0xC0` to zero before the indirect `RCREG -> INDF2`
store, not only after increment/wrap.  This is a first-order memory safety
guard on the UART producer: even if the index is later corrupted by another
path, the ISR cannot write current-loop bytes into adjacent bank-2 state.

Host-tool hardening:

- `scripts/dlcp_diag.py --watch` now defaults to the least-invasive path:
  cmd `0x44` only.  Full cmd `0x06` + cmd `0x43` + EP0 route/config probes
  require explicit `--full-watch-probes`; `--cmd44-only` is also available
  for one-shot capture.
- `dlcp_main_flash` refuses to trust EP0 Config/Channels when the filename
  window looks like `BF/2C/00`, `B1/23/00`, or `B2/23/00` chain cadence.
- post-flash filename finalize now read-back-verifies the HID cmd `0x03`
  filename slot and retries/refuses a corrupt `0xBF` readback instead of
  printing it as if it were a valid filename.

Still open: the exact upstream writer that made `rx_ring_wr` invalid on live
hardware is not proven.  Static V3.4 ownership is narrow (boot/resync clear,
ISR increment/wrap, and ring predicates), so the remaining suspects are
indirect memory corruption, EP0/live transport interaction, or another
foreground/ISR scratch/bank issue.  The rev `0xA6` guard prevents this
specific adjacent-RAM damage while preserving that investigation boundary.

## FIELD-10 (WAKE LIFECYCLE / I2C PHASE ORDER, SIM-FIXED in V3.4 rev 0xAC): startup `I6` after guarded lifecycle route drain

Symptom (2026-06-14 live rig, MAIN `V3.4 rev 0xA6`): immediately after hard
power-cycle, both MAINs can report `Runtime: I6 D0 S0 B0 R0 A0 P0` while reset
cause is clean POR and the units otherwise enumerate as healthy enough for
cmd `0x44` diagnostics.  The matching count on both MAINs is not credible as
random bus noise; it is a deterministic startup-path signature.

Meaning of the counter: `I` is MAIN-local `diag_i`, incremented by
`i2c_byte_tx` when `SSPCON2.ACKSTAT` reports NACK and by the bounded MSSP
timeout recovery path.  The observed `R0` rules out timeout recovery for this
specific field sample, so the six counts are ACKSTAT/NACK events.  One TAS
`0x1F` transaction emits exactly six bytes
(`0x68, 0x1F, 0x00, 0x00, 0x00, data`), and the route ladder can also emit
secondary-device writes through the same ACKSTAT-counting primitive.  Therefore
`I6` is consistent with one early route/input-side I2C transaction hitting a
device-not-ready window.

Introduction point: commit `d69d689` (`Fix V3.4 preset DSP safety regressions`,
MAIN `V3.4 rev 0xA4`) replaced the direct wake sequence

```asm
call tas3108_write_zero_volume_coeff
call preset_replay_selected_table_blocking
```

with a guarded lifecycle route:

```asm
call tas3108_write_zero_volume_coeff
bsf  event_flags_b0, 1
bsf  event_flags_b0, 4
bsf  active_flags_acc, 7
call cmd_dispatch_gated
```

That change was justified for FIELD-6/FIELD-7: route/channel sync must run
while muted and before the final validated selected-preset writer, so
route-sync cannot be the last writer into TAS coefficient space before live
audio.  The proof covered coefficient final-writer ordering, but it did not
separate all input-route side effects from the wake device-readiness boundary.
`cmd_dispatch_input_route_if_dirty` runs before the `active_flags.bit7`
lifecycle bypass check; it can reach physical input-route I2C side effects
while wake is still inside the blind hardware re-initialization window.

Fix contract: preserve the `d69d689` coefficient-safety invariant, but split
the lifecycle phases explicitly:

1. Keep audio muted.
2. Drain `event_flags.bit4` route/channel sync before final selected-preset
   reassert, because it can overlap TAS coefficient space.
3. Run the final selected-preset reassert through the FIELD-5 validated
   physical-source/header/NACK-aware row writer.
4. Only after the post-wake device-init barrier (`i2c_secondary_apply_wake_init_table` /
   equivalent) run `event_flags.bit1` input-route physical side effects.
5. Restore nonzero volume only after bit1 has either succeeded or produced an
   operator-visible fault/muted-safe state.

Resolution (V3.4 rev `0xAC`):

- `stock_094.bit6` is the explicit FIELD-10 `barrier_pending` state.
  `stock_094.bit7` is a per-dispatch bit1-attempt marker.
  `event_flags.bit1` is the retryable late input-route phase.
  `active_flags.bit5` owns the automatic/fault mute while `active_flags.bit4`
  keeps the effective mute asserted.
- `cmd_dispatch_gated` services `barrier_pending` before normal active7 work.
  The retry path calls `wake_i2c_barrier_attempt`, which owns
  `i2c_secondary_apply_wake_init_table` plus the secondary `0x1B` wake-tail write.  On
  failure it preserves the barrier, asserts fault-owned mute, suppresses stale
  volume dirty state, and leaves the MAIN in a visible fault/muted-safe state.
- The active7 lifecycle no longer drains bit1 as a preamble.  It zero-mutes,
  drains bit4 route/channel sync, clears bit6, runs the validated selected
  preset reassert through `preset_replay_selected_table_blocking`, then allows filename and
  volume work only after the later FIELD-10 gates.
- `run_wake_rail_gate_and_dsp_cold_init` no longer sets bit1 before active7.  It performs the
  post-wake barrier first; only a clean barrier arms late bit1 and volume
  restore.
- Late bit1 is isolated and retryable.  A bit1 NACK keeps fault-owned mute,
  preserves the pending bit, and blocks nonzero volume until a later successful
  bit1 attempt clears the fault.
- FIELD-10 exploration found two related safety tightenings and they are part
  of this resolution: direct user mute clears `event_flags.bit5` only after the
  verified TAS zero-write succeeds, and preset-table apply now fails fast on a
  pre-existing ACKSTAT latch so active7 cannot clear a zero-mute NACK and then
  start coefficient rows.
- While a USB filename gate holds `filename_dirty_flags.bit6`, the preset job
  now stays force-muted instead of returning immediately with old-preset live
  audio.

Rejected fixes:

- Do not clear or discount `diag_i`; the counter is exposing a real phase-order
  problem.
- Do not add a blind delay or retry loop as the correctness mechanism.
- Do not move the full normal dispatcher earlier again; the fix must name which
  side effects are legal before final preset reassert and which are legal only
  after device init.
- Do not let bit1 run after volume restore.

Required regression coverage:

- Cold boot and wake on the two-MAIN chain must settle with `I0` on both MAINs
  when no explicit I2C fault is injected.
- An injected early-not-ready TAS/secondary window during wake must not produce
  a healthy, unmuted startup with `I6`; the MAIN must remain muted/safe or
  surface fault until the later phase succeeds.
- FIELD-6/FIELD-7 oracles must remain green: route/channel sync cannot be the
  final coefficient writer, and the selected preset image must be golden before
  nonzero TAS `0x30..0x33`.

## Addendum (2026-06-11): findings from the FIELD-3 forensics

1. **Post-wake standby-path bounce.**  Tick-level traces show the wake
   sequence can re-enter the standby path after the Preset entry repaint
   already ran (`'Preset         A'` visible, then blanked 0.3M ticks later
   with the PC inside `app_entry_defensive_stub`'s delay), and a duplicated
   wake press can be consumed twice (one LEFT press from the buggy state
   landed two menu states away).  The FIELD-3 layers make the LCD outcome
   robust regardless; the button/event double-consume itself is a candidate
   for a future dedicated fix.
2. **Stock-latent ISR/foreground scratch collision — FIXED 2026-06-11
   (V1.73 rev 0x44).**  Final mechanism, after two corrected hypotheses:
   the stock RC5 decoder runs BLOCKING inside the ISR (~7-10 ms from the
   first edge) and clobbers access-bank scratch shared with the foreground
   LCD/delay helpers (`0x005`, `0x008`, `0x00C..0x00E`, the `0x010..0x013`
   sample buffer, `0x014/0x015`).  The V1.71 health-suffix patch knew this
   and GIE-masked its own LCD writes -- which protected the LCD at the
   cost of EATING any IR frame that landed inside the mask (RBIF latches,
   but a late-entered blocking decoder cannot sample the frame).  All
   stock LCD sections stayed unmasked, so an IR frame mid-draw corrupted
   the interrupted sequence instead -- the historic LCD-glitch class and a
   credible mechanism for the field FIELD-3 row-0 blank (the wake press
   arrived by IR remote with repeats).  Fix: the ISR saves the full
   shared-scratch set before `rcall ir_rc5_decode` and restores it after
   the result stores (`v173_isr_decode_save`, bank2 0x260..0x26A), and the
   now-purposeless GIE mask in the health patch is retired.  IR decodes
   correctly during foreground LCD/delay activity AND the interrupted
   foreground state survives; the decode logic itself is untouched
   (BUG-IR-01 hardware-validated path).  Tests:
   `tests/sim/test_v17x_isr_scratch_collision.py` (baseline decode pin,
   decode-survives-foreground-delay, count-survives behavioral check
   [skips when the phase-dependent catch cannot be established], and the
   structural save/restore + no-GIE-mask pin).
   Original (superseded) text follows for the record:
   Corrected mechanism after the 2026-06-11 sim reproduction
   (`tests/sim/test_v17x_isr_scratch_collision.py`, 1 baseline pin green +
   2 strict-xfail contracts): the in-ISR RC5 decoder uses `Common_RAM+12/13`
   as its per-edge TIMING scratch and (after the timing phase) as its
   address/command accumulators -- on an idle foreground the decode is
   untouched and correct, so the load-bearing collision is the shared
   delay/timing use, not background accumulation as first hypothesized --
   while every foreground `delay_short_inner_spin_from_w` delay
   decrements the very same cells in place.  When an IR edge interrupts a
   foreground delay loop, both directions corrupt, deterministically
   reproduced: (a) the in-flight foreground count corrupts the decoder's
   edge timing and the frame FAILS TO DECODE -- a silently dropped remote
   press, matching the field symptom "remote is flaky while the display is
   busy"; (b) the decoder residue rewrites the interrupted delay's
   remaining count (observed `0x0019 -> 0x0205`, ~20x inflation) -- LCD
   timing distortion on real hardware.  Present in stock V1.6b; carried
   into V1.7x by the byte-faithful rewrite.  Fix contract pinned by the
   xfails: preserve the foreground's `0x00C/0x00D` across the ISR decode
   (save/restore in the ISR prologue/epilogue, or dedicated decoder
   cells), without touching the hardware-validated decode logic.
3. **Test-arming race fixed.**  The full-sync stepper fires on EXACT
   equality with `0x4E20`; `test_v173_v34_chain_mute_survives_periodic_
   full_sync_refresh` armed the counter at exactly `0x4E20`, racing the
   per-pass increment (a one-increment miss waits a full 16-bit wrap).  The
   test now arms one below (`0x4E1F`), firing within two passes under
   either ordering.

## Addendum 2 (2026-06-11): session-49 mute escape — lost-frame convergence

Exploratory run `20260611_100415_goal_subagents_isr_scratch_20m` session 49:
a held SELECT (the stock mute toggle, which auto-repeats into an
unmute-then-mute pair) left **PB1 unmuted at full volume while CONTROL
displayed Mute and PB2 stayed muted** — a true awake mute-ownership escape.

Forensics (fully deterministic via instrumented replay):

1. CONTROL emitted `B0/03/03` then `B0/03/02`, 41.8M ticks apart.  Both
   frames reached PB1's UART FIFO **byte-perfect** (363/363 TX bytes
   FIFO-accepted, streams identical) and PB2 (downstream through PB1's
   forwarding) applied both.
2. PB1's `cmd03_mute_on_handler` **never executed** for the second frame
   (PC-watch: zero hits across the delivery window); the parser consumed
   the bytes misaligned (caught mid-frame at idle, `fpos=1` with
   `rd==wr`), under the session's sustained TAS-NACK foreground pressure.
   The exact instruction-level loss inside the ring/parser is still open
   (tracked below); the byte-level layer is fully exonerated.
3. Nothing ever healed the divergence: the CONTROL cmd-03 echo path only
   syncs CONTROL *toward* MAINs, and the full-sync mute step's counter is
   reset by every volume frame — session 49's host-volume cadence starved
   it indefinitely.  Mute was the only chain state without a working
   convergence loop.

Fix (V1.73 rev 0x47): **periodic idempotent mute re-assert** — riding the
health-poll cadence, every 2nd successful poll enqueue *while CONTROL is
muted and connected*, re-broadcast `B0/03/02`
(`v173_mute_reassert_div`, bank2 0x26B).  A consistent MAIN no-ops the
redundant frame; a diverged MAIN re-converges within ~2 poll cycles.  The
muted-only gate keeps the idle/unmuted wire byte-identical to rev 0x44
(test phase assumptions hold; the dangerous direction — live audio against
a muted UI — is the one that self-heals).  Replaying session 49 against the
fixed canonical shows both PBs muted and consistent at the original escape
observation point.

Review hardening (codex on `b1f35d6`, fixed in the follow-up): the first
implementation routed the re-assert through `mute_frame_send` ->
`serial_tx_routed_frame`, whose success path clears the full-sync
countdown — so while muted, the mute convergence loop starved the
volume/input/preset full-sync convergence indefinitely.  The re-assert now
enqueues the frame with the raw tx-ring primitives (no full-sync side
effect), STATUS.C is forced back to the poll's result on every re-assert
path, and `test_v173_mute_reassert_does_not_starve_full_sync` pins an
armed full-sync firing while muted with re-asserts flowing.  The
rotation-tolerant LCD helper was also tightened to the scroller's real
bounce behavior (contiguous substrings only, no circular wrap).

Tests: `test_v34_serial_remute_applies_after_recent_unmute` (a chain mute
must always apply regardless of how recently an unmute ran) and
`test_v173_chain_mute_state_converges_after_lost_mute_frame` (a diverged
MAIN re-converges within a bound far tighter than the starvable
full-sync), both in `tests/sim/test_v34_mute_refresh_bug.py`.  Filename
LCD suites made rotation-tolerant where they pinned exact scroll phases.

Residuals tracked: (a) the instruction-level parser/ring loss mechanism
under I2C-retry pressure (forensic breadcrumbs above; affects any single
frame, but every other chain state already had convergence); (b) the
reverse direction — a MAIN stuck muted while CONTROL is unmuted — is not
covered by the muted-only re-assert (cosmetically a silent speaker, not a
safety issue; the cmd-03 echo adopt path partially covers it).

### Addendum 2 resolution (2026-06-11, V3.4 rev 0x83): the loss mechanism

Single-instruction tracing on the pinned run-era binary (the replays had
silently drifted onto the evolved canonical, which masked the bug — the
faithful rev-0x44 hex was restored from git history) landed the exact
mechanism, and it is NOT a ring or delivery race: ring content was
byte-perfect, there is no second runtime ring consumer, and facade reads
were proven non-perturbing (identical outcomes with and without
mid-run register reads).

**The V3.2 parser stall watchdog (`periodic_service_loop__check_rx_frame_gap`) fires
mid-frame inside a normal inter-byte gap.**  The stock parser idles at
`rx_frame_position=1` after every dispatched frame (the data-phase
completion at `1c6e` re-arms fpos=1 by design), so the watchdog's 8-bit
counter — which increments whenever {mid-frame AND ring empty} — silently
accumulates across every inter-frame idle and is never reset when a real
frame starts.  When the carried count is within one inter-byte gap
(~320 us = a handful of loop passes) of wrapping 0xFF→0x00, it expires
BETWEEN a frame's bytes: `clrf rx_frame_position` drops the half-parsed
frame and the remaining bytes are discarded as invalid routes.  Loss
probability ≈ gap-passes/256 per frame — rare, traffic-phase dependent,
and command-agnostic (any frame can be the victim; session 49's victim
was the mute).  Trace: `fpos 1→0 with rd unchanged` at t=542,432,245,
then the 0x03/0x02 bytes consumed-and-ignored at fpos=0.

Root fix: every byte consumed from the RX ring resets the gap-watchdog
counter inside `rx_ring_read` — a consumed byte IS parser progress, so
the counter now measures only a single continuous mid-frame starvation
(its design intent) and can never carry inter-frame accumulation into a
live frame.  True stalls (bytes that never arrive) are still caught.

Regression: `test_v34_frame_dispatches_with_preaccumulated_gap_watchdog`
(pre-accumulates the counter to 0xFE and delivers a frame with realistic
320 us byte spacing; pre-fix the frame silently vanished, post-fix it
dispatches).  The CONTROL-side mute re-assert (rev 0x47) remains as the
defense-in-depth convergence layer for any other single-frame loss cause.
